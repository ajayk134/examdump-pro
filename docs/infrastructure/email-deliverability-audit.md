# Email deliverability audit — ExamDump Mail

Date: 2026-11-11. Environment: production (`examtopicspro.duckdns.org`), Gmail
SMTP relay via `examdump.official@gmail.com`.

This document records measured evidence, not assumptions. Everything below was
observed on real delivered messages read from the mailbox over IMAP, plus public
DNS.

## 1. What we measured

Message headers on delivered mail (`BODY.PEEK[HEADER]`):

```
Return-Path: <examdump.official@gmail.com>
Received: from [127.0.0.1] ([157.151.159.137]) by smtp.gmail.com with ESMTPSA
          id ... (version=TLS1_3 cipher=TLS_AES_256_GCM_SHA384 bits=256/256)
From: ExamDump <examdump.official@gmail.com>
Reply-To: examdump.official@gmail.com
Message-ID: <...@gmail.com>
MIME-Version: 1.0
Content-Type: multipart/alternative; boundary="--_NmP-..."
```

MIME structure (verified on the full body):

| Check | Result |
| --- | --- |
| `multipart/alternative` | present |
| `text/plain` part before `text/html` | present, correct order |
| `charset=utf-8` on both parts | correct |
| `Date` header | present |
| `Message-ID` | present, generated by Google |

So **message formatting is not the cause**. Structure, encoding and ordering are
all correct.

## 2. Authentication headers — the finding

Searched the complete header block of delivered mail for:

| Header | Present? |
| --- | --- |
| `DKIM-Signature` | **no** |
| `X-Google-DKIM-Signature` | **no** |
| `Authentication-Results` | **no** |
| `ARC-Seal` / `ARC-Message-Signature` | **no** |
| `Received-SPF` | **no** |

No DKIM signature of any kind is attached to mail we submit through
`smtp.gmail.com`.

## 3. Why — the actual root cause

Three facts combine:

**a. Our envelope/From domain is `gmail.com`, which we do not control.**

**b. Google's SPF for `gmail.com` does not authorize our IP.**

```
gmail.com TXT: v=spf1 redirect=_spf.google.com
_spf.google.com: v=spf1 ip4:74.125.0.0/16 ip4:209.85.128.0/17
                       ip6:2001:4860:4864::/56 ... ~all
```

Our sending host resolves to `157.151.159.137` (AS31898 Oracle Cloud,
`157.151.128.0/17`). That prefix is **not** in Google's SPF. A receiving MTA
evaluating SPF for the `gmail.com` envelope therefore returns a non-pass result.

**c. `gmail.com` publishes a DMARC policy that quarantines unauthenticated mail.**

```
_dmarc.gmail.com: v=DMARC1; p=none; sp=quarantine; rua=mailto:mailauth-reports@google.com
```

Result for a receiving provider: **SPF does not align + no DKIM + DMARC
`sp=quarantine`** on a domain we cannot authenticate → confidence score drops and
the message is filtered to Spam. This is the mechanism, and it is structural, not
a bug in our code.

**d. Contributing factors**

- Our sending IP has **no PTR (reverse DNS)** record: `dig -x 157.151.159.137`
  returns NXDOMAIN. Receiving MTAs treat missing PTR as a weak reputation signal.
- The IP is a *new* sending source with no accumulated sending history or
  engagement data at any receiving provider.
- Google's DKIM selector `20230601._domainkey.gmail.com` publishes `p=` (empty),
  meaning there is no publicly verifiable key for us to point at. Google signs
  its own web/Gmail-client mail internally; it does not DKIM-sign third-party
  submissions on behalf of a `@gmail.com` From address in a way that survives to
  the recipient as ours.

## 4. What cannot be fixed with a Gmail account

These are **not** implementation defects and no code change can address them:

1. **SPF** — we cannot add an `include:` for our server to `gmail.com`, because we
   do not control that zone.
2. **DKIM** — we cannot publish a selector under `gmail.com`, and Google does not
   sign our relayed submissions.
3. **DMARC** — we cannot publish a policy for `gmail.com`; we are subject to
   Google's.
4. **PTR / rDNS** — controlled by Oracle Cloud. Can be requested from the provider
   for the instance's public IP, but the name would still not be a domain we can
   authenticate against for mail purposes without owning it.
5. **Domain reputation** — `gmail.com`'s reputation is Google's, shared with
   billions of legitimate users; our sending is not differentiated by it.

## 5. What we did fix (safe, in our control)

See `## Improvements applied` below for the verified list.

## 6. The only real long-term fix

Send from a **domain you own**, with:

- `SPF` TXT: `v=spf1 include:_spf.google.com ~all` (relaying through Gmail
  Workspace) or the ESP's include
- A DKIM key published at `<selector>._domainkey.yourdomain`
- `DMARC`: start `p=none` with `rua=`, then move to `p=quarantine`
- A stable PTR on the sending IP if sending directly

A domain such as `examdump.pro` (or any registered domain) pointed at Google
Workspace, or a transactional ESP (Postmark/Resend/SES), would make SPF and DKIM
align and remove this entire failure mode. That is a product/ops decision
involving a domain purchase, not something the codebase can fix.
