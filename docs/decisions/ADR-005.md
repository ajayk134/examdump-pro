# ADR-005: Single host, rootful Podman, no orchestration

- **Date:** 2026-11-12 (recorded retrospectively)
- **Status:** Accepted (with known limitations)
- **Deciders:** project owner

## Context

The product must run in production with real users, on a budget, without a platform
team. The workload is modest: one API process, one Next.js server, one PostgreSQL,
one nginx.

## Problem

What does the deployment topology look like, and how much orchestration is
justified?

## Decision

**One host.** Four containers under **rootful Podman**, orchestrated by
`podman-compose`, fronted by nginx which owns :80/:443. Secrets injected by
Doppler at deploy time. Backups via `pg_dump` scripts on the same host.

No Kubernetes, no Swarm, no managed database, no load balancer.

## Alternatives considered

| Alternative | Why rejected |
| --- | --- |
| Kubernetes (single node or managed) | operational overhead far exceeds the benefit for one host and four containers |
| Docker Swarm | additional abstraction with no redundancy gain on one host |
| Managed PostgreSQL | removes backup/restore burden and adds point-in-time recovery, but adds recurring cost and a network hop; a strong candidate for a future ADR |
| Serverless (Vercel + managed DB) | would split the API from the long-running workers and the in-process queue; the mail worker and cron assume a persistent process |
| Multiple hosts behind a load balancer | the queue and cron are per-process (ADR-002), so horizontal scaling is blocked until workers are separated |

## Advantages

- Minimal moving parts: four containers, one compose file, one reverse proxy.
- Rootful Podman gives predictable volume ownership and port binding for 80/443
  without rootless quirks.
- Cheap: one VM.
- Deploys are a `git checkout` plus `compose up`.

## Disadvantages

**These are real and should be read before relying on the system.**

- **No redundancy.** The host is a single point of failure. If it dies, the site
  is down until it is rebuilt.
- **Backups are on the same host.** A host loss takes the backups with it. Copying
  dumps off-host is not automated — the most serious operational gap in this
  deployment.
- **Two Podman stores on one machine.** A rootless store exists alongside rootful;
  a dead duplicate there has already caused a false "production is down"
  diagnosis. `podman ps` alone is misleading.
- **nginx caches the API IP** at startup; recreating the API requires
  `nginx -s reload` or the site returns 502 while the API is healthy.
- **No monitoring or alerting.** Nothing notices an outage automatically.
- **Not horizontally scalable.** Workers, cron and rate limiting are per process.

## Security implications

- Rootful containers mean a container escape is a root escape on the host. Rootless
  would be safer but complicates binding privileged ports.
- Secrets arrive via Doppler at deploy time and are never on disk — except in the
  container environment, which is readable by root on the host.
- The database is not exposed publicly; only nginx is.
- Keep `PAYMENTS_ENABLED=false` and `UPI_AUTO_APPROVE=false` — there is no
  defence-in-depth beyond the application layer for payment integrity.

## Performance implications

- All inter-container traffic is local — negligible network latency.
- No resource limits are set, so one runaway container can starve the others.
- Vertical scaling only: to handle more load, increase VM size, not instance count.
- A cold start re-populates the dataset cache, adding latency to first requests.

## Consequences

Accepting this ADR means accepting a single point of failure and manual operations.
The following are prerequisites before any claim of high availability:

1. Off-host backups, verified by restore.
2. External uptime monitoring with alerting.
3. Worker separation (ADR-002) before more than one API instance.
4. A managed or replicated PostgreSQL.

Each of those is a significant change and deserves its own ADR.
