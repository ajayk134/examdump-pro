# ADR-002: PostgreSQL-only queue, no Redis

- **Date:** 2026-11-12 (recorded retrospectively)
- **Status:** Accepted
- **Deciders:** project owner

## Context

The system needs background work: sending mail, syncing the dataset, expiring
subscriptions, reconciling payments, observing UPI notifications. Several of these
must be reliable across restarts and must not send the same email twice.

The deployment is a single VM running a handful of containers.

## Problem

What backs the job queue and scheduled work?

## Decision

Use **PostgreSQL as the queue**, and run workers **inside the API process** using
`node-cron` and an in-process interval. Claiming uses
`SELECT ... FOR UPDATE SKIP LOCKED` with a lease
(`MAIL_LOCK_LEASE_SECONDS`). No Redis, no external broker.

Queue state lives in `email_queue` (with `dedupe_key`, `locked_until`,
`next_attempt_at`) and `upi_observer_state`.

## Alternatives considered

| Alternative | Why rejected |
| --- | --- |
| Redis / BullMQ | adds a second datastore, its own persistence and failure mode, and a new secret — for a workload of a few messages per minute |
| RabbitMQ / SQS | operationally heavier; introduces a broker whose state must itself be backed up |
| A separate worker process | would need its own supervision and deployment path; the single-host model makes it unnecessary today |
| `pg-boss` or similar | a dependency that reimplements what one `FOR UPDATE SKIP LOCKED` statement already does correctly |

## Advantages

- **One datastore.** Backups already capture the queue; a restore reproduces
  pending work.
- **Crash-safe.** A lease expiry makes an abandoned job claimable again, so a
  restart mid-batch does not lose mail.
- **No duplicate sends.** `FOR UPDATE SKIP LOCKED` means two workers never claim
  the same row.
- One fewer service to run, monitor, secure and pay for.

## Disadvantages

- **Scaling ceiling.** Worker throughput is bounded by one API process; there is no
  horizontal worker tier.
- **Coupled lifecycle.** A CPU-heavy worker competes with request handling in the
  same event loop.
- **Polling latency.** Mail is sent up to `MAIL_WORKER_INTERVAL_SECONDS` late
  (default 20 s), not immediately.
- In-memory rate limiting and cron scheduling are **per process** — running two
  API instances would double limits and duplicate cron work unless the
  `upsert`/lease logic in each job is carefully idempotent.

## Security implications

- One less network service and one less credential set to manage.
- Queue rows contain recipient addresses and rendered bodies — they are personal
  data and are covered by the same backup-protection rules as the rest of the
  database.

## Performance implications

- The claim query is indexed (`email_queue_due_idx` on
  `(status, scheduled_for)`), so polling is cheap even with an empty queue.
- Polling is the trade-off for not holding a persistent connection to a broker.
- A large campaign batch competes with requests for the connection pool; bound it
  with `MAIL_BATCH_SIZE`.

## Consequences

Before scaling the API horizontally, the worker must be split into a separate
single-instance process, or each job made explicitly cluster-safe. That is a
prerequisite for multi-instance deployment, and is recorded in
[TECH_DEBT.md](../../TECH_DEBT.md).
