# ADR-003: UPI collection via unique amounts and notification matching

- **Date:** 2026-11-12 (recorded retrospectively)
- **Status:** Accepted
- **Deciders:** project owner

## Context

Card payments require a merchant account and a payment gateway, which adds cost,
KYC and provider dependency. A personal UPI VPA can collect money directly with no
gateway — but UPI provides **no callback** for a personal VPA. There is no signed
webhook telling an application that money arrived.

The only available signal is a **bank alert**: an email or SMS saying "Rs.X
credited".

## Problem

How can an application reliably associate an incoming UPI transfer with the order
that caused it, using only such alerts?

## Decision

Give every payment attempt a **unique payable amount**:

```
amount_paise = base_amount_paise + random(0..99)
```

Uniqueness is enforced among *active* orders by a partial unique index:

```sql
CREATE UNIQUE INDEX upi_orders_active_amount_idx ON upi_orders (amount_paise)
  WHERE status IN ('pending','under_review');
```

Creation retries on collision. An incoming alert is parsed for its amount and
matched to the single active order requesting that exact amount. Matching is
**notification-based** and, by default, requires **human approval**
(`UPI_AUTO_APPROVE=false`).

## Alternatives considered

| Alternative | Why rejected |
| --- | --- |
| Merchant UPI with a PSP callback | requires merchant onboarding/KYC and fees; it is the correct long-term path but not available at the outset |
| Ask the payer to enter the UTR after paying | relies entirely on user honesty; a user simply types a fabricated UTR |
| Match on amount alone, allow duplicates | ambiguous when two users pick the same plan — money could be credited to the wrong account |
| Match on a note/remark field | UPI notes are user-editable and frequently dropped by banks |
| Poll a bank API | no such API is available for a personal VPA |

## Advantages

- Works today, with no merchant onboarding and no provider fees.
- Unique amounts make matching unambiguous **by construction**, enforced by a
  database index rather than application care.
- Suffix is bounded to 0–99 paise, so the user overpays by at most ₹0.99 and the
  base price is preserved in `base_amount_paise` for invoicing and refunds.
- Human review by default keeps a fraud check in the loop.

## Disadvantages

- **No bank-verified confirmation.** A notification is a claim that a bank sent
  something; a convincing forgery could satisfy the matcher.
- The user is asked for an unusual amount (`₹499.37`), which requires clear UI copy.
- If a bank alert is never delivered, a real payment goes unmatched and must be
  reconciled manually.
- Notification delivery depends on an email/SMS pipeline the application does not
  control.

## Security implications

This is the crux of the ADR. Because matching is not bank-verified:

- The client can never mark an order paid — no such endpoint exists.
- `upi_matches_order_settled_idx` allows **at most one** approval per order, making
  double settlement impossible even with a replayed notification or two concurrent
  admin approvals.
- `upi_notifications_utr_idx` prevents the same bank reference being counted twice.
- Risk scoring (`services/upi/risk.ts`) scores amount, uniqueness, reference and
  timing — but it is explicitly a scoring function, not proof.
- **`UPI_AUTO_APPROVE=false` is the actual control**: every match is reviewed by a
  human against the real bank statement.

Enabling auto-approval is a residual-risk acceptance decision that must be made
deliberately, not drifted into.

## Performance implications

- Collision retries are bounded and cheap (index lookup).
- The partial index only covers active orders, so it stays small as order history
  grows.
- Each alert triggers a small indexed lookup, not a scan.

## Consequences

- The UPI rail ships disabled (`PAYMENTS_ENABLED=false`).
- Any future change to matching must preserve the partial unique indexes; they are
  correctness constraints, not optimisations.
- Migrating to a merchant/PSP with real callbacks would supersede this ADR, and
  should be recorded as a new ADR rather than edited into this one.
