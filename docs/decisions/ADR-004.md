# ADR-004: Opaque rotating refresh tokens alongside JWT access tokens

- **Date:** 2026-11-12 (recorded retrospectively)
- **Status:** Accepted
- **Deciders:** project owner

## Context

The API is stateless per request and needs cheap authentication. It also needs the
ability to revoke a session — after logout, a password reset, or a suspected
compromise.

A single token cannot satisfy both: a self-contained JWT cannot be revoked, and a
database lookup on every request is the cost a JWT exists to avoid.

## Problem

How to authenticate requests cheaply while retaining server-side revocation?

## Decision

Use **two tokens**:

| Token | Format | Lifetime | Verified by |
| --- | --- | --- | --- |
| Access | JWT, HS256 | `ACCESS_TOKEN_TTL` (15m) | signature only, no DB |
| Refresh | opaque random 48 bytes | `REFRESH_TOKEN_TTL_DAYS` (30d) | `sessions` row lookup |

The refresh token is stored as `sha256(hash)` in `sessions`; the plaintext is
never persisted. It rotates on every refresh — the old hash is replaced, so a
reused old token is detectable. It is delivered in an `HttpOnly`, `Secure`,
`SameSite` cookie.

## Alternatives considered

| Alternative | Why rejected |
| --- | --- |
| JWT only, long-lived | cannot revoke; a stolen token is valid until expiry |
| Opaque tokens for everything | a database round-trip on every request; loses the cheap verify |
| JWT with a server-side denylist | denylist grows unboundedly and still needs a lookup per request |
| JWT with rotating signing keys | does not solve per-session revocation |
| Session cookie + CSRF token | viable, but the API is consumed by a separate origin; bearer access tokens keep it straightforward |

## Advantages

- Access verification is a signature check — no I/O.
- Revocation is immediate and server-enforced: mark the `sessions` row revoked.
- Password reset revokes **all** sessions for that user (`revokeAllSessions`).
- Storing only the hash means a database leak does not yield usable sessions.
- Rotation makes token theft detectable rather than silent.

## Disadvantages

- Two token types to teach and to get right in clients.
- Refresh requires a database write (rotation), not just a read.
- A stolen **access** token is usable for up to 15 minutes — unavoidable without
  per-request checks.
- Clock skew and timezone handling across clients can cause spurious 401s at the
  boundary.

## Security implications

- `COOKIE_SECURE=true` in production; without HTTPS the refresh cookie would be
  exposed.
- `JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` must differ — rotating one should
  not invalidate the other's purpose.
- `PASSWORD_PEPPER` is appended before bcrypt hashing, so a database-only
  compromise cannot be brute-forced offline.
- Constant-time comparison (`safeEqual`) is used for token and hash comparison.

## Performance implications

- Hot path: one JWT verify, no database access. This is the main win.
- Refresh path: one indexed lookup by `refresh_token_hash`
  (`sessions_token_unique`) plus one update.
- Session rows accumulate; pruning expired rows is a maintenance task tracked in
  [TECH_DEBT.md](../../TECH_DEBT.md).

## Consequences

Any new client must implement refresh-on-401. Treating the access token as
long-lived (caching it past expiry) produces intermittent 401s. Guards in
`apps/api/src/lib/guards.ts` are the single place authentication is decided;
routes must use them rather than reading cookies directly.
