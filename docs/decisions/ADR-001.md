# ADR-001: Exam content lives in GitHub, not PostgreSQL

- **Date:** 2026-11-12 (recorded retrospectively)
- **Status:** Accepted
- **Deciders:** project owner

## Context

The product serves exam question banks across 160+ providers. Content is large,
changes frequently, and carries licensing obligations. The application also needs
PostgreSQL for users, progress, payments and audit data.

## Problem

Where should question content live?

Storing questions in the application database would make deployment, updates and
licensing harder, and would mix recoverable customer data with licensed content in
every backup.

## Decision

Question content lives in a **private GitHub repository** (`exam-data`), read
server-side at request time via `packages/data-client` with a read-only token,
cached in-process (TTL + LRU, default 300 s).

PostgreSQL stores **only metadata** (`catalog_providers`, `catalog_exams`) and
user data (`attempts`, `question_results` reference questions by
`provider_id`/`exam_key`/`question_id` string identifiers, not foreign keys).

## Alternatives considered

| Alternative | Why rejected |
| --- | --- |
| Questions in PostgreSQL | content churn requires migrations; backups mix licensed content with customer data; no path to keep content out of a database dump |
| Static JSON bundled into the web build | content updates would need a full redeploy; bundle size grows with the corpus |
| Object storage (S3-compatible) | viable, but adds a service and credential surface for no benefit over the git history already used for review |
| CDN-served static files | leaks content publicly; no per-user slicing possible |

## Advantages

- Content updates are a commit, not a migration.
- Git history gives review and rollback for content.
- Database backups contain no licensed content.
- Free-tier slicing happens in one place, before content leaves the server.

## Disadvantages

- A runtime dependency on GitHub availability; an outage breaks question serving.
- `question_results` become **detached** if a question is removed upstream —
  historical answers keep identifiers but the text is gone.
- In-process TTL cache means each API instance has an independent view.
- Token expiry is a live failure mode with an unclear error (`502`) unless logs
  are read.

## Security implications

- The GitHub token must stay server-side; it is never returned to the browser.
- Content never appears in fixtures, tests or commits — enforced by review and
  gitleaks for secrets, not by an automated content check.
- Answers are withheld from clients at serialisation time
  (`toClientQuestion(q, includeAnswer)`), not by hiding them in the UI.

## Performance implications

- One network hop to GitHub on cache miss; cache hit is in-memory.
- A cold cache after a restart adds latency to the first request per exam.
- No `JOIN` is possible between user progress and question content — this is by
  design, and it is why analytics work on identifiers only.

## Consequences

Any feature that needs to join question content to application data must be
implemented in application code, not SQL. New question-related columns must never
be added to PostgreSQL. A replacement has to keep content out of database backups.
